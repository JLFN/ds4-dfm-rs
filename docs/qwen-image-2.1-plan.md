# Native image generation in ds4-dfm-rs — port plan

[Documentation index](README.md) | [Repository README](../README.md) |
[Roadmap](qwen-image-2.1-roadmap.md) | [Port recipe](qwen-image-2.1-recipe.md)

Status: superseded — the port is stopped. Nothing in this document is
implemented and no branch carries code. Every claim is a citation into a checked
source or is explicitly marked unverified. The [recipe](qwen-image-2.1-recipe.md)
holds the file-and-line reference index; the [roadmap](qwen-image-2.1-roadmap.md)
holds the phase detail and the tracker. This document holds the goal, the
strategy, what the tree lends, the translation map and the risks.

Phase S ran on 2026-10-01 and returned **no capturable gain** on all three
measurements, so the performance case below is dead. The decision unit then
priced the ownership case that was left and the one unclaimed headroom the spike
measured, and **closed the port**: the [decision](qwen-image-2.1-decision.md) is
the authority, the roadmap's tracker records each phase's closure, and this
document is retained as the definition of what was not built. The numbers are in
the [phase-S report](qwen-image-2.1-phase-s.md).


## 1. Goal

**ds4-dfm-rs serves local text-to-image generation on its own engine and host:
one process, the tree's own C/CUDA kernels, a Rust host, no external runner, no
third-party runtime.**

The goal is capability and ownership. A port that reproduces Qwen-Image-2.1
faithfully on this tree's stack and serves it through the API an existing client
already speaks is a success even if it is no faster than the
`stable-diffusion.cpp` binary it replaces. Any speed claim is measured before it
is made; none is assumed.

| Id | Success criterion | Proof |
| --- | --- | --- |
| G1 | A 1024x1024 image is generated by a ds4 process, with no `sd.cpp` binary involved | a run log and the PNG, with the process list showing no `sd-server` |
| G2 | The result matches the reference: byte-identical initial noise, image inside the stated pixel band | the P1 numbers and the image comparison |
| G3 | An existing client works unchanged: the OpenAI images payload the current bridge accepts | a served request from that payload returning a PNG |
| G4 | The engine reports a resolved plan (requested, effective, qualified) and refuses the autoregressive flags by name | `--check-config` output and a test per refusal |
| G5 | A recorded baseline: seconds per step, sampling split from VAE decode, observed clocks | the P6 ledger |

Non-goals for v1: not faster than the reference; no image editing; no Metal; no
training, LoRA or adapter loading; no second serving contract (this engine gets
no KV, banks, prefix reuse, snapshots or MTP, and does not pretend to).

## 2. The strategy: port, don't invent

This is a port. The reference implementation is the authority, and the work is
translation rather than design. Three rules follow, and they set the cost:

1. Translate the reference, do not redesign it. Every model file, constant,
   layout and schedule comes from `stable-diffusion.cpp` at the pinned commit
   (recipe section 1). Where a detail is not read, it is read before it is
   written; nothing is inferred from the shape of a similar model.
2. Vendor an op rather than write one, when upstream has it. This tree already
   vendors 42 files verbatim from llama.cpp's `ggml-cuda` into `cuda/mmq` at pin
   `5c0e9468`, with `ds4_ggml_stubs.{h,cu}` and `ds4_mmq.{h,cu}` letting them
   compile without the ggml runtime ([VENDOR.md](../cuda/mmq/VENDOR.md)). The
   ops this port needs and does not have — `im2col`, `conv2d`,
   `conv2d-transpose`, `upscale`, `pad`, `arange`, group norm inside `norm.cu`,
   masked non-causal attention in `softmax.cu` and `fattn.cu` — come from that
   same upstream by that same route.
3. Reuse this tree's primitives rather than add a parallel implementation.
   Matmul, RMSNorm, RoPE scaffolding, tensor and stream plumbing, graph capture
   and the residency plan already exist here.

Calibration for what that costs. The Bonsai port — a whole model added to this
tree — is 84 lines of primitives (`cuda/qwen35_primitives.cuh`), 65 lines of
Rust (`crates/ds4-core/src/qwen35.rs`), and three commits touching them, with
everything else reused or vendored. That is the shape of a port done this way,
and it is why this plan's size section reads the way it does.

The alternatives are rejected for stated reasons, not by preference. Vendoring
`stable-diffusion.cpp` as a linked engine or a sidecar gives the feature without
the ownership, and puts a second ggml runtime in the build. A third-party tensor
framework is not this path: the native layer is the tree's own kernels.

The one thing this strategy does not buy is speed. Section 4 is explicit about
which of the tree's optimizations transfer to a diffusion workload, and the
answer is: fewer than you would expect.

## 3. What this buys, and what it does not

The list below is the case as proposed. The [decision](qwen-image-2.1-decision.md)
section 3 restates each item as a loss the deployment suffers today and prices
it; two of them do not survive, and the rest were judged not to be worth the
port. The text is kept as proposed so the pricing can be read against it.

Buys:

- One process instead of two. Today an image request goes through a bridge that
  supervises an `sd-server` child with its own hooks, idle reaper and lifecycle;
  that arrangement once served errors for 8h51m behind a dead child. Merged,
  there is one binary, one lifecycle, and one place errors surface.
- One memory policy. Placement is currently `--offload-to-cpu` / `--backend` /
  `--params-backend` decided by the reference and outside ds4's governor; the
  port puts placement, the host floor, the burst reserve and admission in one
  place ([host-memory-guard.md](host-memory-guard.md)).
- One weight path. The DiT GGUF is Q6_K, a type the vendored MMQ covers, and the
  mmap or zero-copy load path applies unchanged.
- No third-party runtime, and no C++ host layer: the work goes into the tree's
  own kernel layer and Rust host.
- The tree's measurement discipline, applied to images: `ds4-perf`'s inspect,
  scout, compare and optimize, the NVTX annotation, the CUPTI collector and the
  proof harness ([ds4-perf.md](ds4-perf.md)).
- Artifact control, later: once the engine is ours, the DiT can be re-quantized
  with this tree's own path, which is where much of the text families' speed
  comes from.

Does not buy:

- Better images. The model is the model; the output distribution is unchanged up
  to kernel precision.
- Speed, until measured. Section 4 explains why the usual levers are thin here.
- A fix for the resolution ceiling. 1024 square inside the client timeout, 1152
  pinned, 1344 failing during weight preparation is a 12 GB VRAM fact. The DGX
  Spark's 128 GB removes it, and that is a deployment change to the existing
  stack, not a port.

## 4. Applicability: what the tree lends, and what it does not

Checked kernel by kernel, not assumed.

Applies, with the evidence:

- Quantized GEMM. The DiT's linears are Q6_K (229 of 297 tensors), which the
  vendored MMQ covers. This is upstream llama.cpp code, the same lineage the
  reference's ggml carries, so the delta against the reference is unmeasured
  rather than assumed.
- Graph capture. A fixed-shape graph executed once per step is the ideal capture
  case, cleaner than autoregressive decode. The stale-argument rule still
  applies: the timestep and sigma are that graph's `pos0`.
- Residency. The CUDA residency plan (`ds4.c:71725`: VMM arena, HBM promote) is
  this tree's own code, and it is what a 12 GB card holding a resident DiT needs
  (measured 2026-10-01 at 7921 MiB of 11894 MiB — see the
  [phase-S report](qwen-image-2.1-phase-s.md) section 4).
- Placement and the offload mode (appendix A.1): per-module tiers, a device
  budget, a fixed staging arena, segmentation with prefetch.
- Admission: the host memory guard owns limits, cgroups and pressure handling.
- Measurement and artifact control, as above.

Does not apply, and the reason is structural:

- The decode family, entirely. A diffusion step is a full-sequence pass at a
  fixed shape; there is no token-at-a-time phase. MMVQ, the `attention_decode_*`
  kernels, the decode row scalars and the fused decode paths have no work to do.
- The KV family — banks, prefix reuse, partial fork, disk KV, snapshots. There
  is no cache. The serving contract defines a bank as a concurrency slot owning
  its own KV and prefill scratch ([serving-contract.md](serving-contract.md)),
  and the attention signatures are built on `raw_kv`, `window`, `sinks_offset`,
  `comp_kv`, `ratio` and `comp_mask` (`ds4_gpu.h:2395-2402`, `2561-2580`).
- Speculative drafting and continuous batching: no drafter, and the reference
  runner asserts batch size 1.
- The MMQ software pipeline, this tree's headline prefill optimization. It is
  gated to four low-bit block types — IQ1_S, IQ1_M, IQ2_XXS and IQ2_XS, the set
  the K2 recipe routes through the worklist, not anything a diffusion artifact
  uses — and to tile widths up to 64
  (`cuda/mmq/ds4_mmq_pipe.cuh:35-40`, attribution at `:28`). The DiT's Q6_K does
  not route through it, and no diffusion artifact on disk is quantized in those
  types. This is the clearest example of a lever that exists here and does not
  transfer.
- The D2R path: a Q2_K MoE down-GEMM (`cuda/mmq/ds4_mmq_d2r.cuh:1-4`). The DiT
  is dense.
- The flash-attention kernel: `head_dim` 128 only, written around compressed
  Solar K/V and a GQA pair, and causal (`cuda/mmq/ds4_fattn.cu:1-28`). The DiT
  is 32-head MHA, non-causal, with per-segment masks and no compression.
- The prefill/decode split. Every step costs the same, so the metrics become
  seconds per step and seconds per image, split between sampling and the VAE
  decode, and the context, sequence-count and MTP flags are meaningless.

There is no head-to-head measurement against llama.cpp or ggml anywhere in this
tree: `git grep` over the tracked docs finds none, and every A/B recorded here is
a kill switch on versus off. Nothing yet establishes that these kernels beat the
ones the reference already runs. Phase S exists to settle that before the port
is committed to, and section 11 states the decision rule.

## 6. Decision: a sibling engine kind, not a model family

The image engine must not enter `ModelFamily`. The enum
(`crates/ds4-core/src/shape.rs:20-34`) is twelve autoregressive text families,
and the family contract ([serving-contract.md](serving-contract.md)) requires
`--ctx`, `--max-seqs`, continuous banks, prefix reuse, disk KV and MTP for every
family. A diffusion engine has no KV to reuse, nothing to admit and no drafter;
forcing it in would make the contract untrue for the whole tree.

The engine is therefore a sibling engine kind at the `Model` level
(`crates/ds4-core/src/lib.rs:561,902` expose `Model` and `Session` with no
engine-kind split today), with its own bridge symbol group, its own refusal set
and its own server surface. Refusals are by name, which is how this tree already
reports an unsupported setting.

## 7. The model, from the reference

Numerics live in the [recipe](qwen-image-2.1-recipe.md); this is the shape.

The deployed artifact is Qwen-Image-2.1, and its DiT is not the 1.0 DiT. The
2.1 runner (`src/model/diffusion/qwen_image_2_1.hpp`) defines its own config,
attention, block and model: 32 blocks, hidden 4096, 32 heads of 128,
intermediate 12288, in/out channels 64, context 4096, axes 16/56/56. Three
things differ from a reading of the 1.0 file, all read from the 2.1 one:

- No spatial patchify: `DiT::patchify(image, 1, 1)` (`qwen_image_2_1.hpp:287`).
- No separate text stream and no `add_q/k/v_proj`: text and image are one token
  sequence laid out in segments, and attention runs per segment with a
  per-segment mask (`:160-186`).
- Modulation is four chunks with `tanh` gating and a prefix/image row split
  (`:200-215`), and the MLP is SiLU-gated (`:226-236`).

The VAE is the Wan causal 3D decoder in its Qwen-Image-2.1 configuration
(`wan_vae.hpp:1072-1090`): `dec_dim` 144, `z_dim` 64, `dim_mult {1,2,4,8,8}`,
temporal flags `{true,true,true,false}`, with a 64-value per-channel mean and
standard deviation plus a scale factor (`:1366-1389`). It is not the 16-channel
Wan2.1 VAE, which is why the DiT's in and out channels are both 64.

## 9. Gap inventory

One gap is not a kernel. The diffusion model ships as GGUF, but the VAE ships as
`qwen_image_2.1_vae_bf16.safetensors`, and this tree reads GGUF only — grep finds
no safetensors reader and `crates/ds4-core/src/gguf.rs` is the sole loader.
Either a one-time converter writes the VAE into a GGUF with a pinned layout, or
a reader is added. The converter is recommended: one format at runtime, and the
same tool can normalize the DiT's missing metadata (appendix B.7). P0 owns it.

The rest are ops this tree does not have today. Verified by grep: `conv2d`,
`conv3d`, `upsample`, `groupnorm` and `pixel_shuffle` appear nowhere in `ds4.c`,
`ds4_cuda.cu`, `ds4_metal.m`, `metal/*.metal` or `cuda/*.cuh`; the only 1D
convolutions are the SSM and MiMo audio ones, and the only 2D spatial op is the
bilinear position resize in `cuda/step37_vision.cuh:32`.

They are not inventions, and that difference is the cost argument. Every one has
a 1:1 reference in the upstream this tree already vendors from: `im2col.cu`,
`conv2d.cu`, `conv2d-transpose.cu`, `upscale.cu`, `pad.cu`, `arange.cu`, group
norm inside `norm.cu`, and masked non-causal attention in `softmax.cu` and
`fattn.cu`. The work is vendoring them and wiring them into two graphs, a
pattern this directory has already proved 42 times.

What has no upstream equivalent and is therefore written here:

1. Modulation: chunk a `4*hidden` vector and apply `tanh`-gated
   multiply/residual against a prefix and an image slice.
2. Affine-free LayerNorm as a standalone op.
3. The three-axis RoPE: the `16/56/56` split with the adjacent-pair convention.
4. Segment attention with per-segment masks over a prefix and a variable suffix,
   assembled on the vendored masked-attention core.
5. Sinusoidal timestep embedding (256, theta 10000) — host-side is acceptable.
6. patchify/unpatchify at `1x1`, which is a reshape and a crop.
7. The Euler sampler loop, CFG batching and the flow schedule.

Metal is out of scope for the first pass. `metal/` carries dense, flash_attn,
norm, rope, softmax, glu, unary, cpy, concat, moe, get_rows, set_rows, sum_rows,
repeat and bin, with no convolution; if a Mac target appears, the same vendoring
route applies to `ggml-metal`, to be confirmed at P8.

## 10. Where ds4 fits this problem unusually well

1. Captured graphs. The DiT is one fixed-shape graph executed once per step, a
   better fit for capture than autoregressive decode, which had to be keyed by
   regime. The trap is this repository's own captured-decode rule: by-value
   kernel arguments bake at queue time and replay stale. In this graph the
   timestep and sigma are exactly that class of quantity.
2. Weights. The artifact is already GGUF at a quant ds4 speaks, and mmap is the
   default load path.
3. Memory. Placement, floor and burst reserve become ds4's decisions instead of
   the reference's flags, including the offload mode of appendix A.1.

## 11. Build order and gates

Phase S comes first because it is the only thing that settles whether the port
buys speed; everything after it was to be justified by ownership regardless of
its result. Ownership did not carry it: S measured no gain and the
[decision](qwen-image-2.1-decision.md) priced the rest, so **no phase below is
started**. Details, work items and the per-phase closure are in the
[roadmap](qwen-image-2.1-roadmap.md).

| Phase | Work | Gate |
| --- | --- | --- |
| S | The decisive spike, standalone: masked non-causal attention at ~4.3k tokens, Q6_K through a pipelined MMQ loop, graph capture plus residency on a 12 GB card | three numbers against the reference's own kernels on the same hardware; if none wins, the port proceeds on ownership grounds only and the plan says so |
| P0 | Catalogue: identify both artifacts, layout expectation, bind plan, engine kind, the format decision | a model-free layout test over both artifacts; AR flags refused by name |
| P1 | CPU reference: the DiT forward, VAE decode, sampler and Philox at F32 | byte-identical noise and token ids against the reference dumps; image within a stated tolerance |
| P2 | CUDA primitives: vendor the missing `ggml-cuda` ops, extend the stubs, write what has no upstream equivalent | per-kernel parity against the P1 oracle |
| P3 | DiT on CUDA: residency, the 32-block graph, capture, the offload path, kill switches | DiT velocity parity with capture on, then an end-to-end image on the oracle's VAE |
| P4 | VAE decode on CUDA: the vendored conv, norm, upscale and attention ops in the block structure | image parity against the oracle, plus decode seconds and peak VRAM |
| P5 | Serving: bridge symbols, Rust crate, routes, field mapping, lifecycle, refusals | a served request from the existing client payload returning a PNG |
| P6 | Performance: the baseline, then the repository's measured optimization loop | a ledger with the baseline, each A/B, the adoption decisions and the clocks |
| P7 | Text encoder (deferred): Qwen3-VL-8B as its own contract | conditioning parity before it replaces the dumped path |
| P8 | Metal (deferred) | — |

P3 and P4 are independent once P2 exists. P1 through P6 consume conditioning
tensors dumped from the reference, so the first deliverable does not depend on
porting a second model.

## 12. Numerics contract

Exact by construction, or the comparison is meaningless: the initial noise
(Philox), the conditioning token ids, and the position ids and RoPE table inputs.
Everything else is a stated tolerance with the residual explained: one DiT
evaluation by correlation and relative RMS, the final image by pixels and mean
absolute difference, and the VAE decode tiled against untiled if tiling is used.

## 13. Verification harness

The reference can dump its own intermediates — token ids, conditioning, per-step
velocity, the final image — and the recipe says where to confirm the switches.
That is what makes a staged port possible. The committed evidence is the numbers,
the artifact hashes and the images; scratch harnesses stay outside the tree.

## 14. Risks

External: the model and its reference move. The pinned revision ships both the
2.1 model file and its own doc, and the model directory holds 27 diffusion model
definitions beside the shared `dit.hpp` and `model.hpp`. A 1:1 port pins one
revision and forks from there.

Decision risks, each evidenced:

- The applied kernels are upstream code, so the speed case rests on phase S
  alone. Nothing in this tree measures against llama.cpp or ggml.
- The captured-graph timestep trap. The repository has paid for this class of bug
  three times in the autoregressive case (`7c4b84d`, `a1cff19`, `8fb3c54`).
- The offload mode and graph capture interact: the staging arena must be fixed so
  a captured graph stays valid. Same failure family as the trap above.
- The offload mode's cost is unmeasured, so it cannot be promised to meet the
  client timeout until P6 measures it.
- Upstream drift: the port forks from `6dcb5bb` and will not follow the
  reference's later models and fixes.
- VRAM contention: the three-module stack totals about 11.5 GB, but on the
  deployed placement only the DiT is on the card. Measured 2026-10-01: the DiT
  needs 7921 MiB (5604 MB of weights plus a 2317 MB compute buffer) of the
  11894 MiB the card offers, leaving ~4 GB spare — see the
  [phase-S report](qwen-image-2.1-phase-s.md) section 4.

Unverified: every effort and timing figure. Nothing has been built or measured;
the phase table is a sequence, not a schedule.

## 15. Rollback

Nothing is shared with the text path. The engine is one Rust module, one `.cuh`
pair, one crate, a vendored op set, and their Makefile targets; dropping them
removes it with no residue, and the working bridge keeps running throughout. No
irreversible step is required at any phase.

## 16. Open questions

1. VAE decode placement. The reference's own files disagree about the VAE's graph
   device and its sensitivity has not been measured there (appendix A.1). Decide
   here from a measurement.
2. Whether the DiT's attention is assembled on the vendored masked-attention
   core or gets its own tiled kernel.
3. Engine surface: its own binary first, or a route group on `ds4-server`. A
   separate binary keeps the autoregressive serving contract untouched and is
   the recommended first surface.
4. Text encoding: port Qwen3-VL-8B as its own family, or keep the encoder
   external and ship generation-only first.
5. Artifact format for the VAE, and whether the converter also normalizes the
   DiT's missing metadata so both artifacts enter by one door (appendix B.7).

## Appendix A. The deployed configuration the port must reproduce

The stack running today is not just "a diffusion model". It is a specific
arrangement with measured placement, a specific request surface and a specific
lifecycle. This appendix lists what it does, so the port does not quietly drop a
part. Sources: `/data/imagegen/imagegen.toml` and
`/data/imagegen/docs/architecture.md`.

### A.1 Placement: modules, tiers, budgets and the offload mode

The engine takes per-module assignments on two axes, and the parameter axis has
three tiers, not two. From the deployed build's own help (`sd-cli --help`):

```
--backend        runtime backend assignment, e.g. clip=cpu,vae=cuda0,diffusion=vulkan0
--params-backend parameter backend assignment, e.g. disk, cpu, or diffusion=disk,clip=cpu
--max-vram       per-device budget in GiB for managed weights and runner buffers
--eager-load     load all params into the params backend at load time instead of lazily
--offload-to-cpu place the weights in RAM to save VRAM, and automatically load them
                 into VRAM when needed
--disable-prefetch          disable asynchronous next-segment weight prefetch
--disable-segmented-compute force monolithic graph execution even when graph cutting is needed
--mmap           whether to memory-map model
```

A parameter therefore lives in VRAM, in host RAM, or on disk, chosen per module,
and the graph that consumes it can run somewhere else again. The deployed
values:

```
--backend         te=cpu,diffusion=cuda0,vae=cpu
--params-backend  te=cpu,diffusion=cuda0,vae=cpu
```

(`imagegen.toml:110-113`). Measured consequences (`imagegen.toml:95-105`,
`docs/architecture.md`):

- It holds about 4.4 GiB less host RAM and about 3.4 GiB less of the VRAM peak
  than sd.cpp's `--offload-to-cpu`.
- Pinning the text encoder's parameters as well cannot complete a 1024-square
  generation on a 12 GB card.
- The DiT must not be pinned if an untiled VAE decode is wanted; pinning it
  starves the decode and forces tiling.
- The VAE's graph device is `cpu` in the standing file, while an earlier
  committed figure paired `vae=cuda0` with `--params-backend vae=cpu`; which one
  the retained images are sensitive to has not been measured.

The offload mode is required, not optional. `--offload-to-cpu` keeps the weights
in host RAM and brings them into VRAM when needed. That is a different thing
from `--params-backend cpu`, which keeps the weights in RAM *and* runs the graph
on the CPU: the first streams into a device graph, the second never touches the
device. This plan needs the first, because a Q6_K artifact and any device
combination that does not fit must still run. (The first draft of this appendix
said the DiT was "about 11 GB"; measured 2026-10-01 it is 297 tensors, 5604 MB of
weights plus a 2317 MB compute buffer, and the ~11 GB figure is the whole
three-module stack. See the [phase-S report](qwen-image-2.1-phase-s.md)
section 6.)
It is a fallback with a measured cost rather than a default: the standing
deployment deliberately moved off it once the per-module assignment fit, and
that assignment holds less host RAM and a lower VRAM peak.

What the mode requires in this tree:

- A residency manager per module: a tier per parameter group (VRAM, host RAM,
  disk), with the graph device chosen independently of it.
- A fixed staging arena in VRAM as the destination, so device addresses stay
  stable while the contents stream. This is what lets the mode compose with
  graph capture: a captured graph bakes addresses, so weights must move into a
  stable arena rather than being relaid out per step.
- Segmentation of the DiT into block groups, with the next group staged while
  the current one computes. The tree already has this pattern with pages rather
  than tensors: the Q5 disk-PLE path prefetches the next chunk's pages while the
  current chunk's decoder layers run, with a lookahead kill switch
  (`docs/ds4-dfm-model-families.md:143-151`).
- A per-device VRAM budget, and the resolve-or-refuse decision that follows from
  it: a layout that cannot meet the client's timeout in the offloaded mode is
  refused by name before the request starts.
- Reporting: the resolved plan names, per module, the graph device, the
  parameter tier, and whether the offload mode is active.

Pieces that already exist to build on: mmap-backed loading keeps weights in host
RAM with no upfront copy, `DS4_CUDA_COPY_MODEL` selects copy-to-device instead,
and the host memory guard owns admission ([host-memory-guard.md](host-memory-guard.md)).
What does not exist is the staging arena, the segmentation and the budget: this
tree has no general streamed-weight path, only the disk-PLE precedent above.

Requirement: the engine's resolved plan names, per module, the graph device and
the parameter tier, in the same requested/effective/qualified shape the served
text families use, and an explicit offload mode exists, is honored, and is
reported.

### A.2 The size ceiling is a property of the layout

The bridge advertises a maximum edge (1152 in the deployed configuration) and
refuses larger requests with a named reason, checked on the final size from both
request paths, because a size the layout cannot hold fails after roughly 35 s
with an opaque backend error. Sizes must be divisible by 32, and the
aspect-ratio plus resolution pair resolves to a concrete width and height.
Requirement: the same refusal from the same resolved plan, with the ceiling tied
to the layout rather than hardcoded.

### A.3 Sampling profile

One profile: the model's own scheduler, `steps` 28 and `cfg_scale` 6.0 by
default (`imagegen.toml:127-128`).

### A.4 Request surface

Fields the current client uses and the bridge honors: `model`, `prompt`, `n`,
`aspect_ratio`, `resolution`, `response_format` (`b64_json`),
`num_inference_steps`, `seed`, `cfg_scale`. The client's budget is 300 s total
and 240 s read.

### A.5 Lifecycle and observability

- An idle timeout releases the backend; the timer never fires while a request is
  in flight, and a stop decision is guarded so a generation is never interrupted.
- Health reports the backend's state, the in-flight count, idle seconds, and the
  live sampling mode with its adapter and schedule.
- Today's supervision exists because the backend is a child process that can die
  behind your back. That failure once left the bridge serving errors for 8h51m
  with a zombie child. In-process, that class of failure disappears. What
  remains is the rule this plan already carries: a request that cannot finish
  inside the timeout is refused with a named reason rather than started.
- The listener is loopback only, with no authentication and no TLS, which is
  why the current bridge is bound to `127.0.0.1` and why it was never exposed.
  The ds4 surface should keep that default: anything wider needs authentication
  that does not exist in this stack today.

### A.6 The artifact

Q6_K is the only diffusion model this plan targets: 229 of its 297 tensors are
Q6_K and the remaining 68 are BF16, with no F32. No adapter is configured in the
standing deployment, so the engine's output is the unmodified base model, and
that is what the parity gate compares against.

### A.7 Out of scope for v1, and not designed out

Image editing through the 2.1 layout's reference-image path, and the int8
convrot encoder. This plan does not cover them and does not design for them. The
uncensored adapter layer is not on this list because the standing deployment
does not need it: it was measured as content behaviour rather than quality, and
it was unset when the retained reference images were made
(`imagegen.toml:164-190`). The only thing kept open for free is the layout's
segment machinery, which the text-to-image path already uses and the reference
path would also need.

## Appendix B. Naming

### B.1 Why this needs deciding at all

Every text model in this tree is a `ModelFamily` variant with an `oracle_name`, a
`SHAPE_*` constant, an environment-variable prefix and a Makefile runbook. The
image engine is not a family (section 6), so it needs names in the same style
rather than borrowing an existing family's. The list below is the proposal; P0
confirms it before any of it appears in code.

### B.2 The names

| Item | Name | Follows |
| --- | --- | --- |
| Engine kind (Rust) | `EngineKind::ImageDiffusion` | a sibling of the text engine, not a `ModelFamily` |
| Model (Rust) | `ImageModel::QwenImage21` | one value per artifact; a second image model adds a value |
| Rust module | `crates/ds4-core/src/qwen_image.rs` | one module per ported model |
| Native graph | `ds4_qwen_image_gpu.cuh` | the `ds4_<model>_gpu.cuh` files |
| Native primitives | `cuda/qwen_image_primitives.cuh` | the `cuda/<model>_primitives.cuh` files |
| Vendored ops | `cuda/ggml_ext/` (new) or the existing `cuda/mmq/` | the vendoring pattern of `cuda/mmq/VENDOR.md` |
| Bridge symbols | `ds4_bridge_image_open`, `_step`, `_decode`, `_plan`, `_free` | the `ds4_bridge_*` ABI, op-shaped instead of family-shaped |
| New crate | `crates/ds4-image` | the pipeline and its HTTP surface |
| Host binary | `ds4-image` | hyphen means the Rust host |
| C oracle | `ds4-image-c`, only if one is wanted | the `-c` suffix means the C oracle |
| DiT identity string | `qwen_image_2_1` | the model's own name |
| VAE identity string | `qwen_image_2.1_vae` | read verbatim from the file's own metadata |

### B.3 Environment variables

The text families use one `DS4_<FAMILY>_MODEL` plus per-diagnostic variables.
The image engine needs three paths, because it is three files, so the prefix
carries them:

```
DS4_QWEN_IMAGE_MODEL     the diffusion GGUF
DS4_QWEN_IMAGE_VAE       the VAE
DS4_QWEN_IMAGE_ENCODER   the text encoder
DS4_QWEN_IMAGE_STEPS     step count for a diagnostic run
DS4_QWEN_IMAGE_CFG_SCALE
DS4_QWEN_IMAGE_SEED
DS4_QWEN_IMAGE_COND      read conditioning from a dump instead of encoding
DS4_QWEN_IMAGE_LATENTS   dump latents
DS4_QWEN_IMAGE_LOGITS    dump one evaluation
DS4_QWEN_IMAGE_OUT       output path
DS4_QWEN_IMAGE_PLAN      print the resolved plan
```

### B.4 Make targets

```
test-qwen-image-primitives   per-kernel parity against the CPU oracle
test-qwen-image-cuda         the DiT graph against the oracle
qwen-image-ref-check         the full pipeline against the reference
qwen-image-plan              print the resolved plan
qwen-image-smoke             a short end-to-end run
```

### B.5 The client-visible name does not change

`Qwen-Image-2.1` is what the deployed configuration and the current bridge's
`/v1/models` already return, and what the client payload names. It stays. This is
what success criterion G3 depends on.

### B.6 The ABI id

`Variant` currently runs 0 through 14 (`crates/ds4-core/src/shape.rs`), and a
family reports one value across the boundary. The image engine is not a variant,
so it gets an engine-kind value; if a number must still cross the ABI it takes
the next free id in that namespace, 15, registered in one place. P0 decides.

### B.7 Identification: the artifacts carry no architecture key

This is the naming problem the artifacts create, and it changes how the engine
enters the tree.

- The diffusion GGUF has no metadata at all: 297 tensors and a metadata count of
  zero, with the names beginning immediately at `img_in.weight`. There is no
  `general.architecture` to route on, unlike every family in the
  [model zoo](../README.md#model-zoo), whose `GGUF architecture` column is
  exactly that key.
- The catalog, read from the file: 32 blocks (0 through 31) of nine tensors each
  — `attn.norm_k`, `attn.norm_q`, `attn.to_k`, `attn.to_q`, `attn.to_v`,
  `attn.to_out.0`, `img_mlp.gate_layer`, `img_mlp.proj`, `img_mlp.out` — plus
  nine ungrouped tensors: `img_in.weight` (64, 4096), `modulation.1.weight`
  (4096, 16384, which is four times the hidden size), `txt_in.text_norm.weight`
  (4096,), `txt_in.in_layer` and `txt_in.out_layer` (4096, 4096),
  `time_text_embed.timestep_embedder.linear_1` (256, 4096) and `linear_2`
  (4096, 4096), `norm_out.linear.weight` (4096, 4096), and `proj_out.weight`
  (4096, 64). Tensor types are 229 Q6_K and 68 BF16; there is no F32.
- The MLP in this artifact is the unfused layout: `img_mlp.gate_layer` plus
  `img_mlp.proj`. The reference also supports a fused `img_mlp.gate_up`; this
  file does not use it, so the port implements the unfused path and adds the
  fused one only when an artifact needs it.
- The VAE is safetensors, not GGUF: 238 BF16 tensors whose own metadata reads
  `modelspec.architecture = qwen_image_2.1_vae`, under four top-level prefixes
  (`conv1`, `conv2`, `decoder`, `encoder`). It carries the encoder too; only the
  decoder is needed.

So identification is structural unless the artifact is normalized. P0 decides
between a name-and-shape signature over the tensors above, and having the
converter — already required for the VAE — write a normalized GGUF that carries
`general.architecture`, so this engine routes like every other model in the tree.
The converter is the recommendation: one door for both artifacts, and one place
to pin the layout.
